1. System Overview

Dorm Manager uses a MySQL relational database with 13 tables managed through Laravel 12 migrations and Eloquent ORM. The schema is centred on a per-room, per-tenant billing model:

  1. A Room has a monthly rate and a maximum capacity.
  2. A Contract links one or more Tenants to a Room for a defined period.
  3. Each month, one Invoice is generated per Room (= contract).
  4. The invoice is automatically split into per-tenant TenantPayment rows (rent ÷ tenant_count).
  5. Each Payment records a transaction and optionally links to the specific TenantPayment it settles.
Role control is provided by the spatie/laravel-permission package, which adds roles, permissions, and model_has_roles tables. Three roles are seeded: owner, employee, tenant.

5. Key Business Rules

5.1 Rent Splitting

rooms.monthly_rate ÷ invoices.tenant_count = tenant_payments.share_amount

The split is computed once at invoice generation and stored immutably in tenant_payments.

5.2 Invoice Status Derivation

Tenant payment statusesInvoice status
All = paidpaid
At least one paid, rest anythingpartial
None paid, all unpaid = overdueoverdue
None paid, all unpaid = latelate
None paid, any late/overdue mixed with pendinglate (escalated)
None paid, all = pending (no due date passed)pending

5.3 Electricity Rate Versioning

Multiple rows in settings with key='electricity_rate' and different effective_from dates. The query: WHERE key='electricity_rate' AND effective_from <= billing_month ORDER BY effective_from DESC LIMIT 1.

5.4 Audit Log Immutability

No UPDATE or DELETE operations on audit_logs exist in the application. No updated_at column. Append-only by design.

5.5 PayMongo Webhook Matching

Match order: (1) tenant_payments.paymongo_link_id → (2) invoices.paymongo_link_id → (3) invoice number in payment description/remarks.
